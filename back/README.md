# Linea CRM — сервер

В монорепозитории четыре Go-приложения. Клиенты обращаются к gateway по HTTP и WebSocket.

| Сервис | Ответственность | Хранилище |
| --- | --- | --- |
| `api-gateway` | Проверяет пользовательский JWT, передаёт ID пользователя в остальные сервисы, маршрутизирует HTTP и WebSocket | Не хранит данные |
| `crm-service` | Ведёт карточки клиентов и их историю, управляет лидами, конверсией в сделки и связями сделок с клиентами | `crm_db` — компании, контакты, настройки полей, история, лиды и сделки |
| `auth-service` | Регистрирует пользователей, управляет сессиями, рабочими пространствами и ролями сотрудников | `auth_db` — пользователи, сессии, коды восстановления, пространства и участники |
| `ai-service` | Управляет ассистентами, перепиской, подключениями Telegram и Twilio, блокировками и статистикой | `ai_db` — ассистенты, чаты, сообщения, Twilio и блокировки |

Auth выпускает JWT с `sub`, равным сохранённому `users.id`. При создании ассистента AI записывает этот ID в `assistants.user_id`. Чтение истории и проверка владельца выполняются в AI. Для внешнего API AI сам находит ассистента по его Bearer-токену. Gateway удаляет пришедшие от клиентов заголовки идентификации и передаёт кабинетным маршрутам проверенный ID из JWT.

## Запуск

Для локального запуска понадобятся Go 1.25.8 или новее и PostgreSQL. Для поиска имён и названий в CRM используется UTF-8 и поддержка ICU в PostgreSQL. На новом экземпляре PostgreSQL откройте `psql -h localhost -U postgres -d postgres` и один раз создайте отдельную базу и роль для каждого сервиса. Команды `\password` запросят пароли интерактивно.

```sql
CREATE ROLE auth_app LOGIN;
\password auth_app
CREATE DATABASE auth_db OWNER auth_app;
REVOKE CONNECT, TEMPORARY ON DATABASE auth_db FROM PUBLIC;

CREATE ROLE ai_app LOGIN;
\password ai_app
CREATE DATABASE ai_db OWNER ai_app;
REVOKE CONNECT, TEMPORARY ON DATABASE ai_db FROM PUBLIC;

CREATE ROLE crm_app LOGIN;
\password crm_app
CREATE DATABASE crm_db OWNER crm_app;
REVOKE CONNECT, TEMPORARY ON DATABASE crm_db FROM PUBLIC;
```

В каталогах `auth-service`, `crm-service`, `ai-service` и `api-gateway` скопируйте локальный `.env.example` в `.env`. Заполните настройки каждого сервиса.

- **Auth** — укажите пароль `auth_app` в `PGPASSWORD` и задайте разные случайные значения для `ACCESS_SECRET` и `REFRESH_SECRET`.
- **AI** — укажите пароль `ai_app` в `PGPASSWORD`. Для ответов модели заполните `OPENAI_API_KEY`. Для Telegram задайте `TELEGRAM_WEBHOOK_SECRET` и публичный HTTPS-адрес gateway в `WEBHOOK_BASE_URL`. Для Twilio тот же адрес задаётся в `BASE_URL`. Номер, SID и токен Twilio передаются при регистрации ассистента.
- **CRM** — укажите пароль `crm_app` в `PGPASSWORD` и внутренний адрес Auth в `AUTH_SERVICE_URL`.
- **Gateway** — скопируйте значение `ACCESS_SECRET` из настроек Auth. Адреса сервисов задаются через `AUTH_SERVICE_URL`, `CRM_SERVICE_URL` и `AI_SERVICE_URL`. При обновлении существующего окружения добавьте `CRM_SERVICE_URL=http://localhost:8083` в `.env` шлюза.

Примеры используют PostgreSQL на `localhost:5432`. Для другого адреса или порта измените `DATABASE_URL` в сервисах с БД. Запустите `go run .` в отдельном терминале из каталога каждого сервиса. При старте Auth, AI и CRM применят встроенные миграции в своих базах. С настройками из примеров AI слушает порт 8081, Auth — 8082, CRM — 8083, gateway — 8085. Проверить gateway можно запросом `GET http://localhost:8085/health`.

Для Docker собирайте каждый образ из каталога его сервиса, например `docker build -t crm-service ./crm-service` из корня репозитория. При запуске передайте настройки через `--env-file` и укажите адреса зависимостей, доступные из контейнера. При нативном запуске и в контейнерах клиентам должен быть доступен только порт gateway. Auth, AI и CRM принимают `X-User-Id` из доверенной сети сервисов.

Экран Customers использует Auth и CRM через gateway. В режиме разработки и локального предпросмотра Vite берёт адрес gateway из `LINEA_GATEWAY_URL` и по умолчанию использует `http://127.0.0.1:8085`. При публикации фронтенда обратный прокси на домене сайта должен передавать пути `/auth/…` и `/crm/…` шлюзу целиком. [Запуск веб-клиента](../front/README.md)

## Рабочие пространства CRM

Клиент входит через `POST /auth/login` с полями `email` и `password`. Для маршрутов ниже он передаёт полученный `access_token` в заголовке `Authorization: Bearer …`. Все пути в таблице даны относительно gateway.

| Метод и путь | Запрос и результат |
| --- | --- |
| `GET /auth/me` | Аккаунт с полями `id`, `email` и списком `workspaces`. У нового аккаунта список пуст. Каждый элемент содержит `id`, `name`, `role`. |
| `POST /auth/workspaces` | Тело `{"name":"Отдел продаж"}`. Создаёт пространство с ролью `admin` у создателя. |
| `GET /auth/workspaces/:id` | Возвращает ID, название и текущую роль участника в пространстве. |
| `GET /auth/workspaces/:id/members` | Возвращает состав команды. У участника есть `user_id`, `email` и `role`. |
| `POST /auth/workspaces/:id/members` | Администратор добавляет зарегистрированный аккаунт по `{"user_id":"…","role":"sales_manager"}`. Для пилота сотрудник передаёт администратору свой ID из `/auth/me` по известному рабочему каналу. |
| `PATCH /auth/workspaces/:id/members/:user_id` | Администратор меняет роль через `{"role":"head_of_sales"}`. Права пересчитываются при следующем запросе с тем же access-токеном. |
| `DELETE /auth/workspaces/:id/members/:user_id` | Администратор отзывает доступ сотрудника. Успешное удаление возвращает `204`. |

Роли пространства — `sales_manager` (менеджер продаж), `head_of_sales` (руководитель), `support` (поддержка) и `admin` (администратор). Один аккаунт может иметь разные роли в нескольких командах. Auth проверяет членство по своей базе. При обращении к чужому пространству клиент получает `404`, при попытке управлять составом без административных прав — `403`. Повторное добавление участника и попытка снять последнего администратора возвращают `409`.

### Восстановление пароля для пилота

Оператор проверяет личность сотрудника по согласованному каналу и в каталоге `auth-service` с настроенным `DATABASE_URL` выполняет `go run ./cmd/password-reset -user-id <id>`. Команда выводит одноразовый код. Оператор передаёт его сотруднику лично. Код действует 15 минут, повторная выдача заменяет предыдущий код.

Пользователь передаёт код и новый пароль в теле `POST /auth/password/reset` через gateway. Формат запроса — `{"token":"…","password":"…"}`. В рабочем окружении используйте HTTPS. Успешный ответ `204` означает, что пароль изменён и все refresh-сессии аккаунта отозваны. Ранее выданные access-токены действуют до конца своего срока (по умолчанию 15 минут).

## Компании и контакты

Все маршруты ниже используют префикс `/crm/workspaces/{workspace_id}` и access-токен в заголовке `Authorization: Bearer …`. ID пространства клиент получает из `GET /auth/me`.

| Операция | Компании | Контакты |
| --- | --- | --- |
| Создание | `POST /companies` | `POST /contacts` |
| Чтение карточки | `GET /companies/{id}` | `GET /contacts/{id}` |
| Изменение отдельных полей | `PATCH /companies/{id}` | `PATCH /contacts/{id}` |
| Список и поиск | `GET /companies?q=…` | `GET /contacts?q=…&company_id=…` |
| История карточки | `GET /companies/{id}/history` | `GET /contacts/{id}/history` |
| Запись о взаимодействии | `POST /companies/{id}/interactions` | `POST /contacts/{id}/interactions` |

Для создания компании передайте, например, `{"name":"Орбита","email":"office@example.test"}`. В ответе `201` будет карточка с `id`, `workspace_id`, `owner_id`, полями компании и временем создания и изменения. Затем используйте полученный ID в `POST /contacts`, например `{"name":"Алия Ким","position":"Директор","company_id":"<id компании>"}`. Ту же компанию можно указать у нескольких контактов. По умолчанию для самостоятельного контакта достаточно имени.

У компании и контакта есть поля `name`, `email`, `phone`, `tags` и `segment`. У контакта дополнительно есть `position` и `company_id`. PATCH принимает изменяемые поля и возвращает обновлённую карточку. Например, `{"phone":"+7 700 000 00 00"}` изменяет только телефон, а `{"company_id":null}` отвязывает контакт от компании. Владельцем новой компании и самостоятельного контакта становится создатель. При привязке контакт получает владельца выбранной компании, при отвязке сохраняет текущего владельца.

Теги и сегмент задаются для каждой карточки. Например, PATCH с телом `{"tags":["VIP","Партнёр"],"segment":"key"}` заменяет набор тегов и задаёт сегмент. В запросе допускается до 20 тегов по 50 символов и один сегмент до 80 символов. Сервер удаляет пробелы по краям и сохраняет первое написание повторяющегося тега без учёта регистра. Если пропустить поле в PATCH, его значение сохранится. Чтобы очистить классификацию, передайте `{"tags":[],"segment":""}`. У существующих карточек после обновления базы значения этих полей пустые.

#### Поиск и фильтры

Списки компаний и контактов принимают следующие параметры. Условия применяются совместно в пределах доступных пользователю карточек.

| Параметр | Значение |
| --- | --- |
| `q` | Подстрока имени или названия, почты, телефона либо должности контакта. Регистр букв не учитывается. |
| `tag`, `segment` | Один тег и один сегмент. Каждый фильтр ищет точное значение без учёта регистра. Неиспользуемые фильтры опускаются. |
| `owner_id` | ID ответственного сотрудника. |
| `company_id` | Только для контактов. Возвращает контакты указанной компании. |
| `sort`, `order` | Поле `name`, `created_at` или `updated_at` и направление `asc` или `desc`. По умолчанию — `name` и `asc`. При равных значениях порядок задаёт ID карточки. |
| `limit`, `offset` | Размер страницы (по умолчанию 50, максимум 100) и число пропускаемых записей (по умолчанию 0). |

Например, `GET /crm/workspaces/{workspace_id}/companies?tag=VIP&segment=key&sort=updated_at&order=desc` возвращает ключевые компании с тегом VIP в порядке от недавно изменённых к более старым.

| Роль в выбранном пространстве | Чтение и поиск | Создание и редактирование |
| --- | --- | --- |
| `sales_manager` | Свои карточки | Свои карточки |
| `head_of_sales`, `admin` | Все карточки команды | Все карточки команды |
| `support` | Все карточки команды | Доступно только чтение |

Перед каждым запросом CRM получает актуальную роль сотрудника из Auth. Отзыв членства действует при следующем запросе с тем же JWT. Недоступная запись или компания для привязки дают `404`. Попытка записи с ролью поддержки даёт `403`. При недоступности Auth CRM возвращает `503`.

### Настройка полей карточек

У каждого пространства два набора полей. В маршрутах ниже `{kind}` принимает `companies` или `contacts`. Идентификатор пространства передаётся в общем префиксе `/crm/workspaces/{workspace_id}`.

| Метод и путь | Кто может вызвать | Действие |
| --- | --- | --- |
| `GET /fields/{kind}` | Любой участник | Список полей с атрибутами `id`, `label`, `required` и `builtin`. |
| `POST /fields/{kind}` | Администратор | Создание текстового поля. Например, `{"label":"БИН","required":true}`. Ответ `201` содержит созданное поле и его UUID. По умолчанию поле необязательное. |
| `PATCH /fields/{kind}/{id}` | Администратор | Изменение метки или обязательности. Например, `{"required":false}`. Значения в карточках сохраняются при переименовании. |

У встроенных полей можно менять обязательность почты, телефона, сегмента и тегов, а у контактов также должности и связи с компанией. Имя обязательно всегда. Пользовательская метка занимает от 1 до 80 символов и должна быть уникальной в наборе полей без учёта регистра. Совпадение меток возвращает `409`.

Для записи собственного поля передайте его UUID в `custom_fields`, например `{"custom_fields":{"e34a0955-c267-49d8-8533-c527e0ab53cd":"123456789012"}}`. Значение — текст до 2000 символов. Максимальный размер тела запроса к карточке — 1 МиБ. При PATCH передавайте только изменённые ключи. Значение `null` или пустая строка очищает необязательное поле. В карточке `custom_fields` содержит заполненные значения. История хранит метку на момент изменения, а также прежнее и новое значения.

Сервер проверяет итоговое состояние карточки. После включения обязательности старые карточки доступны для просмотра и записи взаимодействий. При следующем сохранении карточки сотрудник должен заполнить недостающие обязательные поля. Незаполненное обязательное поле или UUID из другого типа карточки или пространства возвращают `400`. Роль для каждого запроса определяется по актуальному членству в пространстве.

### История карточки

GET возвращает события от новых к старым. Параметр `limit` принимает значения от 1 до 100, по умолчанию 50. Для следующей страницы передайте полученное строковое значение `next_cursor` в `before`. Значение `null` означает конец списка. Пример ответа при запросе одного события приведён ниже.

```json
{
  "items": [{
    "id": "105",
    "kind": "updated",
    "actor_id": "6a4ccac6-1675-46a5-98c3-4177e53867ac",
    "created_at": "2026-11-23T10:30:00Z",
    "body": "",
    "changes": {"phone": {"before": "", "after": "+7 700 000 00 00"}}
  }],
  "next_cursor": "105"
}
```

Создание карточки сохраняет событие `created`. При изменении `updated` содержит прежнее и новое значения каждого изменённого поля, включая компанию и владельца контакта при его переносе. Сервер записывает событие и карточку одной транзакцией, а автора определяет по авторизованному пользователю. Повторный PATCH с теми же значениями сохраняет прежнее время изменения и пропускает запись в журнал.

Для ручной записи отправьте, например, `{"kind":"call","body":"Согласовали время следующей встречи"}`. Допустимые значения `kind` — `note`, `call`, `meeting` и `email`. После удаления внешних пробелов текст должен содержать от 1 до 4000 символов. Ответ `201` содержит одно событие с текстом в `body` и пустым объектом `changes`. Такие события фиксируют факт общения. Отправка писем и обработка звонков через провайдеров запланированы на этап 9.

Права на историю определяются по текущей карточке. Менеджер может читать историю и добавлять взаимодействия в своих карточках, руководитель и администратор — во всех карточках команды. Поддержке доступно чтение. После передачи контакта другому владельцу прежний менеджер получит `404` при обращении к его истории и взаимодействиям.

Миграция `004_customer_history.sql` применяется при запуске CRM и создаёт таблицу `customer_history`. У ранее созданных карточек история начинается с первого изменения или ручного взаимодействия после обновления. Запрос к такой карточке до первого события вернёт `{"items":[],"next_cursor":null}`.

## Лиды и сделки

Миграция `006_leads_and_deals.sql` применяется при запуске CRM. Все пути ниже используют тот же префикс `/crm/workspaces/{workspace_id}` на gateway и Bearer-токен сотрудника.

| Метод и путь | Действие |
| --- | --- |
| `GET /leads`, `GET /leads/{id}` | Список доступных лидов или одна карточка. Поле `converted` показывает, был ли лид преобразован. Поле `deal_id` содержит ID доступной пользователю сделки, иначе `null`. |
| `POST /leads` | Создаёт лид. Обязателен `title` (до 200 символов), дополнительно можно передать `description` (до 4000 символов) и `owner_id`. По умолчанию ответственным становится автор. |
| `PATCH /leads/{id}` | Обновляет указанные поля открытого лида. Если лид уже преобразован, возвращает `409`. |
| `POST /leads/{id}/convert` | Создаёт сделку с ответственным из лида. Все поля запроса необязательны. При пустом теле или `{}` название берётся из лида. |
| `GET /deals`, `GET /deals/{id}` | Список или карточка сделки с ответственным, ссылками на лид и клиентов, суммой, валютой, плановой датой, вероятностью закрытия, а также `pipeline_id`, `stage_id` и `status`. |
| `GET /deals/board` | Канбан выбранной воронки. Возвращает по каждому этапу общее число доступных сделок после фильтрации и страницу карточек. |
| `PATCH /deals/{id}` | Обновляет ответственного (`owner_id`), параметры, этап (`stage_id`) и связи с клиентами в одной транзакции. Для связей принимает `company_id`, `add_contact_ids` и `remove_contact_ids`. Для отвязки компании передайте `{"company_id":null}`. |
| `GET /deals/{id}/history` | История параметров, переходов и смены ответственного от новых событий к старым. Принимает `limit` от 1 до 100 (по умолчанию 50) и курсор `before` из `next_cursor` предыдущей страницы. |

Пример тела запроса конверсии — `{"title":"Поставка оборудования","company_id":"<UUID компании>","contact_ids":["<UUID контакта>"]}`. Первая конверсия возвращает `201`. Повтор возвращает `200` с текущей сделкой, если сотрудник по-прежнему имеет к ней доступ. Если сотруднику доступен только исходный лид, повтор вернёт `409`. Уникальность сделки на лид и транзакция защищают от двойного клика и одновременных запросов. До 100 контактов можно привязать при создании или позже. Добавление и снятие связей применяются целиком. Повторное добавление сохраняет одну связь.

При конверсии и редактировании можно передать, например, `{"amount":"1250000.50","currency":"KZT","expected_close_date":"2027-03-31","probability":70}`.

| Поле | Формат |
| --- | --- |
| `amount` | Строка с неотрицательной десятичной суммой, до 14 цифр в целой части и до четырёх после точки. В ответе всегда четыре знака после точки. |
| `currency` | Трёхбуквенный код ISO 4217. Сервер возвращает его в верхнем регистре. |
| `expected_close_date` | Календарная дата `YYYY-MM-DD`. |
| `probability` | Целое число от 0 до 100 включительно. |

В сохранённой сделке сумма и валюта либо заполнены вместе, либо обе равны `null`. Чтобы очистить их, передайте `{"amount":null,"currency":null}`. Дату и вероятность можно очистить по отдельности через `null`. Пропущенные в PATCH поля сохраняют свои значения. Нулевая сумма и вероятность 0% допустимы.

Миграция `007_deal_terms.sql` оставляет у прежних сделок все четыре поля пустыми. История возвращает объект `{"items":[],"next_cursor":null}`, пока нет событий. При конверсии с заданными параметрами появляется событие `created`, при изменении — `updated` с автором, временем и значениями `before` и `after` в `changes`. Повторная конверсия и сохранение тех же значений не дублируют события.

Менеджер продаж работает со своими лидами и сделками. Руководитель и администратор работают со всеми записями пространства и могут передавать открытые лиды, а также открытые и закрытые сделки. Поддержке доступно чтение.

Чтобы передать сделку, отправьте `PATCH /deals/{id}` с телом `{"owner_id":"<ID участника>"}`. CRM проверяет в Auth актуальную роль в этом пространстве. Получателем может быть менеджер продаж, руководитель или администратор. Недопустимый получатель даёт `400`, отсутствие права на назначение — `403`. Если Auth недоступен, сервер отвечает `503`. Успешный запрос возвращает обновлённую сделку. Событие `updated` сохраняет автора, время и `changes.owner_id` с прежним и новым ID. Повтор назначения текущего владельца пропускает запись в историю.

После передачи таблица, поиск, канбан и история учитывают нового ответственного. Прежний менеджер теряет доступ к сделке и её истории. Исходный лид и клиентские карточки сохраняют своих владельцев. Если новому менеджеру недоступен исходный лид, в карточке сделки `lead_id` равен `null`.

Связи сделки отображаются с учётом текущих прав читателя на клиентов. Закрытая для менеджера компания представлена как `null`, в `contact_ids` входят только доступные контакты. Изменение доступных контактов сохраняет остальные связи. Попытка привязать недоступного клиента возвращает `404`.

Оба списка принимают `q`, `limit` (по умолчанию 50, максимум 100) и `offset`. Поиск лида учитывает название и описание, поиск сделки — название. Лиды упорядочены по последнему изменению, сделки — по времени создания, от новых к старым.

### Фильтры сделок и канбан

`GET /deals` и `GET /deals/board` принимают одинаковые фильтры. Их можно сочетать.

| Параметр | Что отбирает |
| --- | --- |
| `pipeline_id`, `stage_id` | Сделки указанной воронки или этапа по UUID. Для доски `pipeline_id` обязателен. |
| `owner_id`, `q` | Сделки ответственного и совпадения в названии сделки без учёта регистра. |
| `currency`, `amount_min`, `amount_max` | Сделки в указанной валюте ISO 4217. Обе границы включены, каждую можно опустить. Для диапазона нужна валюта. Формат суммы совпадает с форматом в карточке сделки. |

Например, `GET /deals?currency=KZT&amount_min=100000&amount_max=500000` вернёт доступные сотруднику сделки в тенге на сумму от 100 000 до 500 000 включительно.

Доска возвращает массив объектов с `stage_id`, `total` и `items` в порядке настроенных этапов. У пустой колонки `total` равен нулю и `items` пуст. И карточки, и счётчики учитывают область доступа сотрудника. Если этап принадлежит другой воронке, доска возвращает `[]`. Запрос доски чужого пространства или чужой воронки возвращает `404`.

Для загрузки следующей страницы одной колонки передайте тот же `pipeline_id`, её `stage_id` и остальные активные фильтры. Параметры `limit` и `offset` действуют внутри каждой колонки. По умолчанию `limit=50`, максимум 100. Миграция `009_deal_board_paging.sql` добавляет индекс для этого порядка выборки. Чтобы переместить карточку, используйте `PATCH /deals/{id}` с целевым `stage_id`.

### Воронки и этапы

Все маршруты доступны через тот же префикс рабочего пространства. Настройки читает любой участник, изменяет администратор.

| Метод и путь | Действие |
| --- | --- |
| `GET /pipelines` | Возвращает массив воронок с `id`, `name`, `is_default`, `version` и упорядоченным массивом `stages`. У каждого этапа есть `id`, `name` и `kind`. Основная воронка идёт первой. |
| `POST /pipelines` | Создаёт воронку по имени и массиву этапов. Возвращает созданную конфигурацию и `201`. |
| `PUT /pipelines/{id}` | Принимает полную конфигурацию с текущей `version`. Для существующих этапов передайте их ID, для новых — имя и тип. Порядок элементов задаёт порядок этапов. Возвращает сохранённую конфигурацию. |

Пример тела запроса для воронки продлений.

```json
{"name":"Продления","stages":[{"name":"Переговоры","kind":"open"},{"name":"Продлено","kind":"won"},{"name":"Отказ","kind":"lost"}]}
```

Для воронки нужен хотя бы один открытый этап и по одному этапу успешного и неуспешного закрытия. Названия воронок уникальны в пространстве, а названия этапов — в своей воронке. Регистр букв при проверке уникальности не учитывается. Имя и порядок существующего этапа можно менять, а его тип задаётся при создании. Сервер вернёт `409`, если версию уже изменил другой администратор или если удаляемый этап занят сделками.

При конверсии лида поле `stage_id` позволяет выбрать открытый этап любой воронки пространства. Без этого поля используется первый открытый этап основной воронки. Миграция 008 назначает этот этап ранее созданным сделкам и сохраняет прежнюю историю.

Для перемещения передайте `{"stage_id":"<UUID целевого этапа>"}` в `PATCH /deals/{id}`. Сервер определяет воронку и статус по целевому этапу. Тип `won` или `lost` закрывает сделку, тип `open` открывает её снова. Права на переход совпадают с правами на редактирование сделки. В истории ключи `stage` и `pipeline` содержат снимки ID и имени до и после перехода, `status` — прежний и новый статус. Появляются только изменившиеся поля. Повторный переход в текущий этап сохраняет прежнюю историю.

## Как добавлять модуль

- В `internal/modules/<имя>` размещаются операции модуля и его зависимости. Для работы с таблицами сервиса SQL и миграции лежат в `internal/modules/database`.
- `main.go` загружает конфигурацию, создаёт долгоживущие модули и собирает `internal/app.App`. Здесь же он отвечает за закрытие пула PostgreSQL.
- `internal/api` получает `App` при регистрации маршрутов. Конструктору обработчика передаются модули, нужные конкретному маршруту. Например, в auth обработчик получает модуль авторизации, а сам модуль получает хранилище при запуске.

### Резервные копии PostgreSQL

Для контрольного восстановления нужны PostgreSQL CLI и три новые пустые базы под управлением соответствующих ролей. Пример использует имена подключений из файла служб libpq и пароли из pgpass. Настройте `auth_source`, `crm_source` и `ai_source` для исходных БД, а подключения с суффиксом `_restore` — для отдельных пустых БД. Каталог архивов должен быть доступен только оператору. На время согласованной копии трёх БД приостановите запись.

```sh
pg_dump -Fc -f auth.dump "service=auth_source"
pg_dump -Fc -f ai.dump "service=ai_source"
pg_dump -Fc -f crm.dump "service=crm_source"
pg_restore --exit-on-error --single-transaction -d "service=auth_restore" auth.dump
pg_restore --exit-on-error --single-transaction -d "service=ai_restore" ai.dump
pg_restore --exit-on-error --single-transaction -d "service=crm_restore" crm.dump
```

После восстановления сравните число пользователей, членств, компаний, контактов, чатов и сообщений с источником. В проверочном окружении войдите тестовым аккаунтом, откройте его компанию, связанные контакты и историю его ассистента. Для пилота предстоит настроить ежедневный запуск с хранением копий 30 дней в выбранном месте развёртывания.

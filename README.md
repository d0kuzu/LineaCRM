# Linea CRM

Корневая папка проекта для совместного размещения фронтенда и бэкенда.

## Структура

- `front/` — текущий фронтенд на React, TypeScript и Vite, его настройки и зависимости.
- `front/design/` — макеты и материалы дизайна.
- `front/presentation/` — презентация проекта.
- `front/DEVELOPMENT_PLAN.md` — план разработки.
- `back/` — серверная часть LineaCRM на основе ветки `empty-pattern` проекта `d0kuzu/aveda_ai`. В ней четыре Go-сервиса со своими зависимостями и Dockerfile.

## Бэкенд

Публичная точка входа — `api-gateway` (локально порт 8085). `auth-service` хранит аккаунты, сессии и состав рабочих пространств в `auth_db`. `crm-service` хранит компании и контакты в `crm_db`. `ai-service` хранит ассистентов, чаты и сообщения в `ai_db`. Настройки, запуск и контракт API описаны в [back/README.md](back/README.md).

Первый сценарий для веб-клиента — войти, получить `GET /auth/me` и выбрать одно из доступных пространств. При первой настройке команды пользователь создаёт пространство и получает в нём роль администратора. Роль определяется отдельно в каждом пространстве. Сейчас фронтенд использует демонстрационные данные.

## Порядок разработки CRM

| Этап плана | Что делаем на сервере | Какие экраны подключим |
| --- | --- | --- |
| 2. Клиенты | Готовы создание, просмотр, редактирование и поиск карточек. Контакт может существовать отдельно или быть связан с компанией. Проверены поиск среди доступных записей и отказ для другого пространства. | Компании, контакты, карточка клиента |
| 3. Продажи | Лид, сделка, воронка и этап. Сделка ссылается на компанию и контакты, хранит сумму, валюту, срок и ответственного. Переход между этапами попадает в историю. | Канбан, таблица и карточка сделки |
| 4. Ежедневная работа | Задачи и встречи получают свои ID и ссылки на клиента или сделку. Для календаря нужны время и часовой пояс, для обзора — незавершённые задачи, ближайшие встречи и история активности. Поиск и показатели рассчитываются по доступным записям. | Задачи, календарь, обзор, поиск и аналитика |
| 5–7. Ассистент | Диалог связывается с сотрудником и пространством. При открытии из карточки сервер проверяет доступ к записи. Изменение CRM по предложению модели проходит через то же доменное API после подтверждения. | Боковая панель и экран ассистента |

Маршруты компаний и контактов доступны через `/crm/workspaces/{id}/…` на шлюзе. Шлюз устанавливает личность из JWT, CRM проверяет актуальное членство через Auth и ограничивает выборку по пространству, роли и ответственному. Составной внешний ключ в `crm_db` связывает контакт с компанией того же пространства. Дальше этот же сервис будет владеть лидами, сделками, задачами, встречами и историей изменений.

Когда дойдём до ассистента, `ai-service` будет получать контекст через API `crm-service` от имени сотрудника. Так открытие карточки в браузере и запрос той же карточки из чата пройдут одинаковые проверки доступа.

В исходной ветке уже есть список и поиск чатов, загрузка истории и WebSocket. Текущий WebSocket обслуживает оператора внешнего канала. Отправленное в него сообщение сохраняется как ответ оператора, а для Twilio может уйти клиенту. Для внутреннего ассистента потребуется отдельная отправка от имени сотрудника, создание диалога, идентификаторы сообщений и продолжение истории с последнего полученного сообщения. Идентификатор собеседника внешнего канала `chats.customer_id` и ID контакта CRM нужно связывать явно.

## Запуск фронтенда

Из корневой папки проекта:

```sh
cd front
npm ci
npm run dev
```

Если зависимости уже установлены, достаточно выполнить `npm run dev` в папке `front/`.

## Проверка и сборка

Из корневой папки проекта:

```sh
npm --prefix front run build
```

Команда проверяет типы TypeScript и создаёт сборку в `front/dist/`.

Подробнее о фронтенде — в [front/README.md](front/README.md).
